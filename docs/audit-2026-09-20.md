## 1. Methode

Chaque constat suit le meme patron : la commande est citee, sa sortie est
consignee, et une seconde commande prouve que le capteur est vivant (regle 2
d'AGENTS.md : une sortie vide n'est pas une absence de constat). Les compteurs
sont calcules dans le noyau, pas dans le rendu de la console, parce que le
rendu de ce poste altere les identifiants (piege consigne dans PHASES.md) :
un token cite sans la commande qui l'a produit est une fabrication
(regle 1).

## 2. Constats

### C1 - Deux portes declarees et jamais appelees (corrige dans ce lot)

`verify:kpi` et `verify:reception` etaient des entrees de `package.json` que
rien n'appelait : la liste `DEFAUT` de `scripts/run-all-gates.py` ne les
citait pas, donc `npm run verify:all` les ignorait. Une porte que personne
n'appelle n'est pas une porte (regle 6).

    grep -c 'verify:kpi|verify:reception' scripts/run-all-gates.py  -> 1
    python3 scripts/run-all-gates.py verify:kpi verify:reception
      GATES=2
      RC verify_kpi 0
      RC verify_reception 0
      ROUGES=0

Les deux specs sont joueuses. `reception-view.spec.ts` declare le fixture
`page` : le navigateur est lance et cinq elements du panneau sont trouves,
ce qui est la seule facon de voir un onglet absent (une route sans ecran
n'est pas une fonctionnalite). `kpi-labor-cost.spec.ts` ne declare que
`request` et juge par DELTA : poster, exiger le mouvement, retirer, exiger le
retour. Le nombre de tests reels est de 1 et 1, et non 5 et 1 comme le
comptaient les cinq recherches par `grep -c 'test('` : les occurrences
supplementaires etaient des appels a la methode `RegExp.test`, pas des
declarations. Verdict rendu par le collecteur : `1 passed` dans chaque course.

### C2 - Cinquante-sept routes mutables, zero garde d'identite

    grep -rhoE 'router.(post|put|patch|delete)("[^"]+"' src/routes/*.ts | wc -l
      -> 57
    grep -rniE 'requireAuth|authMiddleware|jwt|bearer|express-session|
passport|bcrypt|api_key|autorisation' src/ server.ts | wc -l
      -> 0   (neuf motifs, zero occurrence)
    grep -rn 'licenseMiddleware' server.ts | wc -l   -> 2
    grep -rniE 'ra.?te.?limit' src/ | wc -l          -> 10

Le seul middleware qui refuse est celui de licence (`server.ts:134`,
`src/middleware/license.ts:15-37`) : il rend 403 quand la periode d'essai est
expiree et que l'application n'est pas deverrouillee, et seulement alors ; les
LECTURES passent, les ECRITURES sont verrouilles de la meme facon, sans qu')
aucune identite ne soit demandee. Le limiteur de debit est un garde, ce n'est
pas une authentification.

Constat : dans le perimetre du produit (un poste, une cuisine, un restaurant
en salle), le modele de deploiement est mono-utilisateur et mono-tenant ; le
produit ne connait qu'un seul utilisateur, celui qui l'exploite. Le defaut
n'est pas une faille tant que ce modele tient. Il le devient des la premiere
mise en reseau multi-postes. RISQUE CONSIGNE, hors du perimetre du lot : non
resolu, a traiter avant toute exposition reseau. Proprietaire : le maitre
d'ouvrage.

### C3 - Une ecriture qui rend 404 et n'inscrit rien

`src/components/InventoryAudit.tsx:156` poste le corps de la cle `items` a
`/api/inventory/bulk`. Le routeur `src/routes/inventory.ts` ne declare que
trois POST (lignes 35,351,439,). La sonde
`scripts/probe-inventory-bulk.mjs`, jouee pendant la campagne, rend :

    POST /api/inventory/bulk -> 404
    corps: null

Consequence : l'import CSV de l'auditeur ne dechiffre rien et n'inscrit rien
en base ; la voie est muette. La porte `verify:inventory-bulk` n'est PAS
branchee dans ce lot, volontairement : la sonde rend un code de sortie a zero
dans les deux cas, la route presente ou la route absente, donc la brancher
telle quelle serait une porte verte qui ne juge rien (la famille du defaut
`verify:forecast` du Sprint 10). Le defaut est porte a la liste des articles
ouverts (section 4) ; la porte y sera branchee, avec sa preuve de morsure
`-mord`, dans le commit qui implementera la route.
