# Inventaire des tests muets (`.skip`) — T3.3, 31/10/2026

## Constat : le fait 13 du planning etait un FAUX POSITIF

Le planning (`docs/planning-reparation-2026-10-31.md`, fait 13) affirmait :

> 7 occurrences de tests `.skip` — commande : `grep -rn "\.skip(" test src | wc -l`

Rejouee le 31/10, cette commande rend **0**, pas 7.

Preuve (commandes executees ce jour, capteur valide) :

- `grep -rnE "\.skip\(" test src` → **0** (aucune occurrence).
- `grep -rnF ".skip(" test src` → **0** ; meme bilan pour `.only(`, `.todo(`,
  `it.todo`, `test.todo`, `describe.only`, `describe.skip`, `it.only`,
  `test.only` : **0 chacun**.
- Le capteur est vivant : le meme grep sur un motif qu'on sait matcher
  (`\.test\(`) rend 35 ; le temoin `process.exit(`/`sys.exit(`/`SystemExit` rend
  21 lignes. Donc le 0 ci-dessus n'est pas un silence du capteur (regle AGENTS.md §2).

**Cause du faux positif** (re-mesurée le 2/11 — la première explication écrite
ici était fausse, voir plus bas) : la commande du fait 13 ne filtrait pas les
fichiers **non suivis par git**. `grep -rn "\.skip(\|test\.skip\|describe\.skip\|it\.skip"
test src` matche les **journaux de portes** `test/gates-run-all-gates.py-*.out`,
où la sortie de morsure contient la chaîne `it.skip factice`.

Mesure du 2/11 :

- `grep -rn "\.skip(\|test\.skip\|describe\.skip\|it\.skip" test src | head` →
  3 lignes, **toutes** dans `test/gates-run-all-gates.py-*.out`, aucune dans un
  fichier de test ni dans `src` ;
- la même recherche restreinte à l'index git :
  `git grep -E "\.skip\(|test\.skip|describe\.skip|it\.skip" 5a5a616 -- test src`
  → **0**.

Donc la bonne commande est `git grep` (elle ne voit que le suivi), ou un `grep`
qui exclut `test/*.out`. Le chiffre « 7 » du planning venait du nombre de lignes
de journaux présentes ce jour-là, pas de tests sautés.

**Rectification** : la version initiale de ce document affirmait que `.skip(`
était une sous-chaîne de `process.exit(`. C'est **faux** et mesurablement faux :
`printf 'process.exit(1)\n' | grep -c "\.skip("` rend **0**. L'explication a été
remplacée par la mesure ci-dessus le 2/11.

## État mesuré des tests

- `npx vitest run` → **188 passed (188), 17 fichiers**, et **aucune ligne
  « skipped »** dans la sortie (le log ne contient pas le mot `skipped`).
- Aucun `test.only` (qui exclurait silencieusement le reste) : 0.
- Aucun `it.skip` / `test.skip` / `describe.skip` : 0.

Conclusion : **il n'y a aucun test muet à inventorier ni à justifier**. La liste
attendue par T3.3 est vide — non pas par absence de recherche, mais par preuve
d'absence (capteur vivant + batterie de 9 variantes + décompte vitest).

## Ce qui remplace la confiance en un capteur cassé

Plutôt que de recopier un chiffre faux, une **barrière déterministe** garde la
règle « aucun `.skip` muet » :

- `scripts/verify-no-mute.py` (`verify:no-mute`) : rougit sur tout
  `it|test|describe(.each(...))?.(skip|only|todo)(` dans `test/` et `src/`, et
  refuse de certifier « vert » si son grep témoin (`process.exit`/`sys.exit`)
  tombe à 0 (`CAPTEUR_SUSPECT rc=2`) — c'est exactement l'angle mort du fait 13.
- `scripts/verify-no-mute-mord.py` (`verify:no-mute-mord`) : la morsure. Elle
  injecte un `it.skip` factice dans `test/.morsure-no-mute/` (zone **scannée**,
  jamais un `tmp-*` qui serait exclu), exige que la barrière **rougisse et nomme**
  le fichier (M2), puis vérifie le retour au vert après retrait (M3). Jamais
  l'arbre jugé n'est touché.

Ainsi, un `.skip` introduit demain casse le lot (`npm run verify:all`) au lieu
de passer sous un grep qui ne le voit pas.
